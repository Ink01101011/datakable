- Search: new opt-in option `search({ fuzzyMaxRows })` for large data. When the data array has more rows than `fuzzyMaxRows` (every row, before filters, so results do not change while the user filters), matching runs as with `fuzzyMaxDistance: 0`: exact, prefix and substring matches keep their scores and order, a query with a typo no longer matches, and no word index is kept. At 100k rows with `fuzzyMaxRows: 50_000`, the first one-word query goes from about 117 ms to about 60 ms and later one-word keystrokes from about 52 ms to about 31 ms (Node, median of fresh processes), and filter + sort + a one-word query takes 3.21 MB instead of 4.37 MB. New data crossing the limit is matched in its own mode from its first search, with no score kept from the other mode. Development builds report `DK_SEARCH_FUZZY_OFF` (info) once per data array when the limit switches typo matching off; `Infinity` means never, like omitting it; an invalid value (not a non-negative integer or `Infinity`) is `DK_INVALID_OPTION`, and with a `searchFn` it is `DK_OPTION_NO_EFFECT`, like `fuzzyMaxDistance`. Omitted (the default), nothing changes. (#123)
- `@datakable/core` depends on `exsorted` 1.3.0 (was 1.2.3). `timSort`, `radixSort` and `countingSort` keep their behaviour; 1.3.0 changes only `timSort`'s default comparator, which DataKable never uses (it passes its own), so sort results are unchanged. (#123)
