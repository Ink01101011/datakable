- Search: a one-word query with fuzzy matching on (the default) no longer splits every cell into words on each keystroke. The words of each cell are found once per data array, a block of rows at a time within the time slices, and kept (ex-search's word index, up to a cap: see the next point); a new data array finds them again on its first one-word query. How much a keystroke gains depends on the text and on how much of the word index fits the memory allowance (next point). Steady one-word keystroke at 100k rows against datakable 2.1.1 from npm (Node, production, median of 5–12 interleaved fresh processes): one searched column of `name N` values, about 82 → 56 ms (−31 %); 4 searched columns of two- or three-word text, 112 → 94 ms (−17 %) on one vocabulary and 152 → 133 ms (−12 %) on another (part of their index is kept); one column of 30-word cells 195 → 165 ms; of 100-word cells about 514 → 494 ms. From about 150k rows up no words are kept and a keystroke splits them again, as in 2.1. The first one-word query on a data array, which also finds and counts the words it keeps, takes about 3–7 % longer than in 2.1.1 on the 4-column text above (161 → 170 ms and 149 → 154 ms, 8 + 8 interleaved fresh processes; another round read +4 % / +7 %). Whole-value matching (queries with spaces, `fuzzyMaxDistance: 0`) keeps one matcher over all rows, and a time slice now ends closer to its deadline: under a 4x CPU throttle the longest task of a first query over 100k rows goes from about 29 ms to about 18 ms, and of a first one-word query over 10 mixed columns from about 42 ms to about 23 ms. Results are unchanged: a randomised differential against a cold search covers edits, filters, query sequences and data spanning several blocks. (#96)
- Search memory: the search state of a data array stays within an allowance of 2 MiB: 10 bytes per data row for the scores kept between keystrokes (#95; a 2-byte code into a table of the match's distinct scores, was an 8-byte number: 16 → 10 bytes per row in all), up to 4 bytes per hit, and the kept words (about 1 byte per word of a multi-word cell, none for a one-word cell) in what is left: about 0.66 MiB at 100k rows, 1.3 MiB at 50k, none from about 150k rows. Rows whose words do not fit have them found again on every one-word keystroke, as in 2.1, with the same results. The §9.3 memory scenarios at 100k rows, all within 5 MB (budget harness): filter + sort + a one-word query 3.80 MB (was 3.93 MB in 2.1), and over 4 columns of two- or three-word text 4.35 MB with a query that hits most rows and 3.56 MB with one that hits a third; over one 30-word column 4.54 / 3.59 MB; zero-config over 10 mixed columns 2.90 MB, with filter + sort 4.70 MB; one column of 30 or 100 words per cell 2.83 / 2.96 MB. Long text is also matched in fewer rows per time slice, and hits are ranked in time slices, so under a 4x CPU throttle no task of a one-word query over 100k rows of 30- or 300-word cells exceeds 50 ms (it was 88 ms and 64 ms). For long text at large row counts, `fuzzyMaxRows` turns typo matching off and keeps no words. (#124)
- `@datakable/core` depends on `ex-search` 2.1.1 (was 1.2.1). ex-search 2.0 trims the query, no longer matches objects and arrays as text and skips `null` rows; DataKable already trims the query and hands ex-search its own formatted strings, so for valid options the rows and their order are unchanged (checked against results recorded with 1.2.1, including padded queries, `null` / `undefined` cells and object / array columns with and without a `search` weight). ex-search 2.x rejects a non-finite weight or threshold; a column `search: Infinity`, or in production a `NaN` / `±Infinity` `threshold`, searches as in datakable 2.1.1 (the same rows, order and status, checked against the published 2.1.1): DataKable hands ex-search finite values and scores those configurations as 1.2.1 did. In development builds too: a non-finite column weight is accepted as before; a non-finite `threshold` is still `DK_INVALID_OPTION`, as in 2.1.1. Matching now relies on ex-search's `search(query, { within })`: an `ex-search` older than 1.2.1 (forced through an override) gets the built-in exact / prefix / substring matching, from the ESM and the CommonJS build alike, reported in development with `DK_DEP_INCOMPATIBLE`. (#123)
