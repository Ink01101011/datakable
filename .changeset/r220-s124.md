- Search: a one-word query with fuzzy matching on (the default) no longer splits every cell into words on each keystroke. The words of each cell are found once per data array, a block of rows at a time within the time slices, and kept (ex-search's word index); a new data array finds them again on its first one-word query. At 100k rows a one-word keystroke goes from about 113–117 ms to about 66–71 ms, and at 1M rows from about 1.1–1.2 s to about 0.7–0.8 s (Node, median of fresh processes); with 4 searched columns of two- or three-word text, from about 111 ms (datakable 2.1.1 from npm) to about 75 ms. Whole-value matching (queries with spaces, `fuzzyMaxDistance: 0`) keeps one matcher over all rows, and a time slice now ends closer to its deadline: under a 4x CPU throttle the longest task of a first query over 100k rows goes from about 29 ms to about 18 ms, and of a first one-word query over 10 mixed columns from about 42 ms to about 23 ms. Results are unchanged: a randomised differential against a cold search covers edits, filters, query sequences and data spanning several blocks. (#96)
- Search memory: the kept words cost about 1–1.6 bytes per searched cell (none for a one-word cell), so every §9.3 scenario stays within 5 MB at 100k rows: 4.38 MB for filter + sort + a one-word query (was 3.93 MB, and 5.57 MB with ex-search 1.2.1's word index), 3.58 MB for a zero-config one-word query over 10 mixed columns (was 2.95 MB). (#124)
- `@datakable/core` depends on `ex-search` 2.1.1 (was 1.2.1). ex-search 2.0 trims the query, no longer matches objects and arrays as text and skips `null` rows; DataKable already trims the query and hands ex-search its own formatted strings, so for valid options the rows and their order are unchanged (checked against results recorded with 1.2.1, including padded queries, `null` / `undefined` cells and object / array columns with and without a `search` weight). One difference, for invalid options only: ex-search 2.x rejects a non-finite weight or threshold, so a column `search: Infinity`, or in production a `threshold` outside 0–1 that development rejects with `DK_INVALID_OPTION`, now fails the search step (`DK_FEATURE_FAILED`) and keeps every row. Matching now relies on ex-search's `search(query, { within })`: an `ex-search` older than 1.2.1 (forced through an override) gets the built-in exact / prefix / substring matching, reported in development with `DK_DEP_INCOMPATIBLE`. (#123)
