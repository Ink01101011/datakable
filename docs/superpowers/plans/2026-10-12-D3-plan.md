# D3 — How to fix (troubleshooting by symptom + error reference)

Job datakable-docs-v1, unit D3, branch `feat/core-D3` from `feat/core-V1`.

## Decisions

- **Docs URL:** `diagnostics/build.ts` keeps `…/blob/main/docs/errors.md`. The reference moves to
  `docs/how-to-fix/errors.md`; `docs/errors.md` becomes a stub with one `### DK_*` heading per code
  (same anchor) linking to the moved section, plus the old `##` section anchors. Every published
  URL keeps working, no runtime string changes, no bundle cost. A new errors-doc test checks the
  stub forwards every registered code.
- `docs/reading-type-errors.md` → `docs/how-to-fix/reading-type-errors.md`, old path a stub with
  the same anchors. Its blocks become complete compiled examples (`// @ts-expect-error` on the
  failing line); `reading-type-errors.test.ts` compiles them with the directives blanked and checks
  each ```text block against what TypeScript prints (`…` = elided text).
- Troubleshooting examples import `datakable` (what users install). A root vitest alias maps
  `datakable` / `datakable/messages` to source, so tests run the shown files.

## Steps (test-first per page)

1. Move both pages, update errors-doc tests (path, `repoPath` depth), add stub test, write stubs.
2. Rewrite reading-type-errors examples + test.
3. Symptom pages, each: symptom → likely causes → how to confirm → fix (compiled) → related codes.
   A `how-to-fix.test.tsx` reproduces each symptom and shows the documented fix removes it.
4. `docs/how-to-fix/README.md`: symptom table + code index.
5. Gate: lint, build, typecheck, test, check:pkg, check:budgets.
