# F2 — Memory: every 100k-row scenario ≤ 5 MB (§9.3)

Baseline (develop c43948f, `pnpm check:budgets`, real default preset on dist): paginated
filter + sort 2.22 MB · unpaginated 7.47 MB · client search applied 16.39 MB.

Probe breakdown (Node, no pointer compression: 8 bytes per array slot): 90k `Row` objects 5.5 MB
(still 4.1 MB with two fields, so a flyweight `Row` is not enough); search: projection items
`{ i, c0, c1, c2 }` 7.6 MB, formatted `id` strings 3.05 MB, formatted `age` / `name` arrays 0.77 MB
each, `name` values 0.77 MB, `id` values 0.76 MB, the filtered subset array 0.7 MB.

## Steps

1. **Lazy rows** (`pipeline/row.ts`, `pipeline/runner.ts`): `RowModel.rows` stays a real array
   (`Array.isArray`, `length`, index access, iteration, array methods) but is a `Proxy` over a
   sparse array that builds a `Row` the first time an index is read and keeps it (stable
   identity). Reflection (`Object.keys`, descriptors) materialises everything. Row keys are still
   resolved over all rows in `build()` (scan diagnostics unchanged); a key read that throws while a
   row is materialised later is reported then (never silent).
2. **Lean search index** (`features/search/search-index.ts`, `search.ts`): no per-row projection.
   The index keeps one reader per searchable column — the column cache's formatted array, or, for a
   numeric column without `format` and without `NaN`, its `Float64Array` stringified per chunk
   (`String(v)` = the default formatter). The matcher walks the input indices in chunks of 4096 and
   builds that chunk's `{ i, c0, … }` items (lower-cased there) for ex-search, then drops them. No
   subset array: the input `Uint32Array` is matched directly.
3. **Column cache** (`pipeline/column-cache.ts`): the default-formatted array of a column whose
   values are already the strings shown is the values array itself (copy-on-write on the first
   differing cell).
4. Budgets: turn each met scenario's ratchet into the enforced 5 MB spec budget
   (`budgets/memory.budget.test.ts`).

## Out of scope

- ex-search itself (its per-search result copies are transient; nothing it allocates is retained).
- Bundle-size work (F3), spec text (F1), `create-table.ts`.
- Changing `RowModelContext` (no new public contract).

## Result (`pnpm check:budgets`, real default preset on dist)

| Scenario (100k rows) | Before | After |
|---|---|---|
| filter + sort, paginated | 2.22 MB | 2.21 MB |
| filter + sort + client search | 16.39 MB | 3.48 MB |
| filter + sort, unpaginated | 7.47 MB | 1.98 MB |

All three are now enforced at the 5 MB spec budget. Note: `arr.length = n` and `new Array(n)`
allocate `n` slots in V8 (0.78 MB at 100k), so the lazy targets use a sparse array instead.
Bundle: createTable +261 B gzip, default preset +307 B (ratchets raised by 0.5 KB with the reason).
