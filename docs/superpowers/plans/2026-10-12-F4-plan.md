# F4 — `datakable` preset + react ≤ 20 KB gzip

Job datakable-core-v1-budgets, unit F4 (implementer). Base: develop 00299a8.

## Goal

Every `datakable` size entry — `createTable`, `useDataTable`, `DataTable` — at or under the §9.3
budget (≤ 20 KB gzip) by `pnpm size`, by making the code smaller; never by raising a budget.
User decision 2026-10-13: `searchFn` (the async search path) is split out of `search()`.

## Baseline (develop 00299a8, `pnpm size`)

| Entry | gzip |
|---|---|
| core `createTable` | 14,759 B |
| `datakable` `createTable` | 27,966 B |
| `datakable` `useDataTable` | 29,708 B |
| `datakable` `DataTable` | 32,925 B |

Attribution (esbuild metafile, the committed method, bytes in the minified output, gzip share
pro rata), `DataTable` entry, top: `search.js` 8.6 KB min, `create-table.js` 7.7, react
`data-table.js` 7.7, `sorting.js` 5.7, react `use-data-table.js` 4.9, `runner.js` 4.3,
`pagination.js` 3.1, filter `match.js` 2.8, `explain.js` 2.8, diagnostics `build.js` 2.6,
`redact.js` 2.6, `column-filters.js` 2.5, `search-index.js` 2.4. The bare core table alone is
14.4 KB of the 20 KB.

## Steps (each measured with `pnpm size`)

1. **Split `searchFn`** (approved): `withSearchFn(fn)` from a new entry
   `@datakable/core/search-async` brands the function with the async search engine (requests,
   abort, stale-while-error, SSR deferral, result mapping); `search({ searchFn: withSearchFn(fn) })`.
   A plain `search()` no longer bundles it. Same pattern as F3's `withFetcher`. Types: `searchFn`
   takes only a wrapped function. Tests migrate mechanically (wrap), none weakened.
2. **Option schemas in development only**: feature option schemas are read only by the dev option
   validator; production keeps the values (`<DataTable />`'s async-source check, `explainRow`).
3. **Further measured cuts** in the preset/react path (duplicated helpers, prod-only strings,
   module structure) as the attribution shows; each kept only with all tests green.
4. Lower every ratchet that shrank to its measured size rounded up to 0.5 KB.
5. Docs: spec §6.3 (searchFn opt-in, stale "memoised per data + columns" text), §12 entries,
   READMEs, `docs/errors.md` examples.

## Out of scope

- Raising any §9.3 budget or ratchet.
- Changing the default preset's features (§3.3) or any spec-required production behaviour.
- The open user questions from RA (prod guard for unwrapped schema/fetcher; whether the 15 KB core
  budget covers only bare `createTable`).
- Publishing, tagging, merging.

## Outcome (`pnpm size`, gzip B)

| Entry | before | after | budget |
|---|---|---|---|
| core `createTable` | 14,759 | 14,765 | ≤ 15 KB met |
| core + filters + sorting + pagination | 22,394 | 21,662 | (core budget, unmet) |
| core + … + search | 27,465 | 23,990 | none |
| `datakable` `createTable` | 27,966 | 24,419 | ≤ 20 KB **unmet** |
| `datakable` `useDataTable` | 29,708 | 26,141 | ≤ 20 KB **unmet** |
| `datakable` `DataTable` | 32,925 | 29,393 | ≤ 20 KB **unmet** |

Steps: `searchFn` split −2,182 / −2,162 / −2,145; option schemas dev-only −759 / −755 / −744;
version registry + `DK_DEP_INCOMPATIBLE` dev-only −606 / −650 / −643.

Why 20 KB is not reachable without a spec change: the bare core table (14.4 KB, budget 15 KB) +
the five preset features (~9.7 KB: filters/sorting/pagination +6.9 KB, search +2.3 KB, validity and
preset wiring +0.4 KB) is already 24.4 KB before any React code (hook +1.7 KB, component +3.3 KB).
