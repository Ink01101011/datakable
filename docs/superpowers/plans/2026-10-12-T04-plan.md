# T04 — Interceptor core: implementation plan

**Goal:** operation registry, `defineInterceptor`, chain compiler and ctx pool in
`packages/core/src/intercept/`, ported from the brainstorm prototype (`icpt.ts`, `opt.mjs`).
Spec: §3.4 (plus §8.1 for the ctx fields, §9.1/§9.2 for the hot-path rules).

**Done when:** type tests (sync op + Promise = error); compile-once verified; overhead bench recorded
(below).

## Files

| File | Responsibility |
|---|---|
| `intercept/operations.ts` | `Operations` interface (type registry, open to declaration merging), `OpName` / `OpInput` / `OpOutput` / `OpResult`, runtime registry (`registerOperation`, `getOperation`) seeded with the §3.4 table |
| `intercept/context.ts` | `InterceptorContext<O>` (`op, input, where, table, run, trigger, phase, meta, emit, signal?`), `createContext`, `createContextPool` |
| `intercept/define.ts` | `Interceptor<O>`, `defineInterceptor` |
| `intercept/runtime.ts` | `createInterceptorRuntime`: chain compiler + cache, `setInterceptors`, `installBoundary` slot, throw-skip semantics, hot-op warning hook |
| `intercept/index.ts` | module barrel; `src/index.ts` gets added export lines only |
| `intercept/*.test.ts`, `intercept/types.test-d.ts` | unit + type tests |
| `intercept/chain.bench.ts` | `vitest bench`: empty compiled chain vs direct call (cold op, `column:batch`) |

## Steps (test-first)

1. Type tests (`types.test-d.ts`): sync op `next()` is not a Promise; async op `next()` is a Promise;
   `data:ingest` accepts both; `@ts-expect-error` for a Promise from a sync op, a wrong output type, an
   unknown op; `'*'` gives the union ctx; an op added by declaration merging is usable.
2. Registry tests: built-in ops present with kind + hot flag; `registerOperation` adds an op,
   re-registering identically is a no-op, conflicting re-registration throws.
3. Runtime tests: order (first listed = outermost); `'*'`; compile-once per op (counted through the
   `onCompile` hook) and recompile after `setInterceptors`; throwing interceptor is skipped and reported
   through `onInterceptorError` (before `next`, after `next`, async rejection) without running the core
   twice and without swallowing errors from inside `next`; boundary slot is outermost, survives
   `setInterceptors`, cannot be installed twice; hot op without `hot: true` → `onHotWarning` with the
   cost in the message.
4. Pool tests: `acquire` reuses released objects, resets `meta`/`signal`, nested acquire returns
   distinct objects.
5. Implement until green, then bench and record numbers here.

## Decisions the spec left open

- **Type registry = interface + declaration merging**, runtime registry = `registerOperation`. Later
  tasks (features, react `render:*`) add both. `render:table` / `render:cell` are *not* seeded in core;
  `@datakable/react` registers them.
- **`'sync|async'`** (`data:ingest`): `next()` returns `Out | Promise<Out>`; the interceptor may return
  either.
- **Order:** the first interceptor in the list is the outermost. The boundary slot is outside all of them.
- **Throwing interceptor:** if it throws before calling `next`, `next` is called directly; if it throws
  after `next` returned, the result `next` produced is returned (the core never runs twice); an error
  that came out of `next` is rethrown untouched (it belongs to an inner layer / the core). Async ops
  apply the same rules to a rejected promise.
- **`'*'` and hot ops:** a `'*'` interceptor attaches to hot ops too, so it gets the hot warning unless
  `hot: true`. The warning fires once per (interceptor, op) when the list is set, not per call.
- **Ctx pool** is a free list (safe for re-entrant/nested runs of the same op), not a single shared ctx.
- `table`, `emit` are loose placeholders until T07 / T05.
- Ops with no result declare `output: undefined` (biome `noConfusingVoidType`); cores and
  interceptors for them may still omit `return` (TS 5.1+).
- `runtime.run(op, ctx, core)` takes the core per call (`NoInfer` so `op` decides the types); the
  chain itself is compiled once per op. Ops registered after the runtime was created are compiled on
  first use, then cached.

## Out of scope

- `errorBoundary` itself, fallback registry, `DK_INTERCEPTOR_FAILED` (T06) — only the slot and the
  `onInterceptorError` hook exist here.
- Diagnostics catalog / routing the hot warning to diagnostics (T05).
- `createTable` wiring and real `table` type (T07); the `column:batch` loop body (T06/T10).
- Glob patterns in `on` such as `'pipeline:*'` (the §3.4 built-in table uses them as shorthand only).
- Runtime detection of a sync-op interceptor returning a Promise from untyped JS.
- Prod stripping of the hot warning (`NODE_ENV`) — default handler is `console.warn`; T05 replaces it.

## Bench results

Machine: Apple M4 Pro, macOS (Darwin 25.6.0), Node v25.2.1, vitest 5.0.3 (bench via the
`bench` test fixture — vitest 5 replaced the top-level `bench()` export).
Command: `pnpm vitest bench --run --project 'core (bench)' --reporter=verbose packages/core/src/intercept/chain.bench.ts`

Cold op (`pipeline:step`, trivial core, reused ctx), 1M calls per sample:

| Variant | mean / 1M calls | per call |
|---|---|---|
| direct call | 0.53 ms | ~0.5 ns (V8 inlines it) |
| compiled empty chain | 4.49 ms | ~4.5 ns |
| compiled chain, 1 pass-through interceptor | 10.82 ms | ~10.8 ns |

Hot op (`column:batch`, `toFixed` format over 5 columns × 100k rows, pooled ctx), per sample:

| Variant | mean | vs direct |
|---|---|---|
| direct loop (inline try/catch) | 21.88 ms | — |
| compiled empty chain + pooled ctx | 19.95 ms | within noise (rme ±1.5%; run order effect) |
| compiled chain, 1 pass-through interceptor + pooled ctx | 20.51 ms | within noise |

Reading: the chain costs ~4–11 ns per call, so cold ops (a handful of calls per run) and hot ops at
batch granularity (one call per column per run) are both far inside the §9.3 "≤ +10% per column
batch" budget. The cost only matters if something is intercepted per cell, which the design forbids.
The hot-op warning quotes these numbers.
