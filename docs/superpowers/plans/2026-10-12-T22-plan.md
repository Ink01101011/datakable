# T22 — Standard Schema ingest (spec §5.1) — implementation plan

## Scope
- `ingest/standard-schema.ts`: the Standard Schema v1 interface, types only (no runtime dependency).
- `ingest/schema.ts`: per-row validation of `options.data` inside the `data:ingest` core, for sync
  and async schemas; `invalidRows: 'drop' | 'flag' | 'throw'`; `DatakableSchemaError`;
  `getInvalidRows()` records `{ index, raw, issues }`; per-data-reference memo (WeakMap).
- `ingest/schema-codes.ts`: `DK_SCHEMA_INVALID_ROW`, `DK_SCHEMA_CRASHED` (issues redacted through
  the `schemaIssues` redact kind → `scrubSchemaIssue`, T26).
- Options: `schema` and `invalidRows` table options (catalog entries, read once; `invalidRows`
  other than `'drop'` without `schema` → `DK_OPTION_NO_EFFECT`).
- Types: `T` inferred from `InferOutput<schema>` (single `createTable` signature, no overload, so
  existing type errors keep their text); `data` is `unknown[]` with a schema; `invalidRows: 'flag'`
  makes `getRowModel().rows` a `FlaggedRow<T>` union narrowed on `valid`.
- Row: `valid`, `issues`, `getCellIssues(id)` (issue path ↔ column key prefix match, both ways).
- Status: async schema → `status: 'validating'` with a new row model + notification at start and
  end (never silent). R5 finding: a failed `data:ingest` (op fallback) sets `status: 'error'` until
  the next good ingest, and fallback data never marks the table loaded (`isInitialLoad` stays true).
  The errorBoundary marks failure on `ctx.meta` (`FAILED`), so failure is detected for sync and
  async ingests alike.

## Steps (test-first)
1. `ingest/schema.test.ts`: drop / flag / throw, getInvalidRows, crash (sync throw, async reject),
   async schema, memo, redaction of messages under 'safe'/'keys', NO_EFFECT, invalid option.
2. `pipeline/status.test.ts`: failed ingest → 'error' (sync, async), not loaded on fallback,
   'validating' transitions notified.
3. `ingest/schema.test-d.ts`: inference of `T`, `FlaggedRow` union narrowing, `getInvalidRows` type.
4. Implement; gate.
