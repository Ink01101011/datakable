# T24 plan — default preset + zero-config `createTable({ data })`

Spec §3.1, §3.3, §9.3, §12.

## Where the preset lives

- §3.3 defines `defaultFeatures = [columnFilters(), validity(), search(), sorting(), pagination()]`;
  §3.1 / §12 put the preset in `datakable` ("re-exports react + default preset", "`datakable`
  exposes the default preset") and keep core tree-shakeable (§9.3: core ≤ 8 KB gzip).
- So: core defines the preset as data (`packages/core/src/preset/`: `defaultFeatures`,
  `createDefaultFeatures()`, `DefaultFeatures`), tree-shakeable (pure calls). Core's `createTable`
  keeps installing no features when `features` is omitted, so a bare `createTable` import never
  pulls the five features in.
- `datakable` exports a `createTable` whose `features` default to a fresh preset per table (type
  default `Fs = DefaultFeatures`, runtime `options.features ?? createDefaultFeatures()`). It
  overrides the core `createTable` that `datakable` re-exports through `@datakable/react`.
  `datakable/core` stays the bare core. Passing `features` replaces the preset entirely.

## Steps (test-first)

1. R6 tidy: `features/pagination.ts` → `features/pagination/` (+ `index.ts`); every module index
   exports its diagnostics arrays (data checks, pagination, sorting, step, data mutation,
   versioning).
2. Core preset tests (names / order / fresh instances / works with core `createTable`) → module.
3. `datakable` e2e test: `createTable({ data })` alone; sort, filter, search, paginate through the
   preset API on derived columns; `features` replaces the preset; type test (getState slices + API
   methods, no type arguments; `createTable<User>({ data })` is precise).
4. Measure gzip of core `createTable` alone before / after; gate.

- Per-feature package entries, prod stripping (T36).
