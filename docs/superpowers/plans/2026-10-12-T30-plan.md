# T30 plan — fault-injection harness: every public method × every callback slot

Spec §11 (fault injection), §8.6, §8.3, §6.6, §3.4. Depends on T06, T24 (develop a020243).

## Harness (`packages/core/src/fault-injection/`, new)

- `harness.ts` (test helper, not exported): builds a table with a sentinel row value
  (`SECRET-123`) and sentinel error messages, captures every diagnostic through `onDiagnostic`,
  and checks per diagnostic: catalog code, exact `formatWhere(where)`, non-empty `fix` entries,
  the sentinel absent from the serialized diagnostic. Tracks `unhandledRejection` per test.
- `slots.test.ts`: a table of every user callback slot (`rowKey`, `columns[i].accessor` /
  `format` / `sortFn` / `sortBy` / `sortAlgorithm`, `sorting.algorithm`, custom filter `fn`,
  `schema`, `fetcher`, `searchFn`, `onStateChange`, `onDiagnostic`, `diagnostics.redact`,
  `interceptors[i].intercept`, `subscribe` listener, `setState` updater, feature `initialState` /
  `createApi` / `rowModel`) × each injection that applies (throw, reject, bad return). Asserts:
  code + exact `where` + `fix`, the registry fallback (observable effect), a usable row model,
  status per the status rule, no rejection where the contract says never-reject.
- `methods.test.ts`: every public table method and every built-in feature API method called while
  each slot fails: never throws, returns its declared value, row model stays usable.
- `batch.test.ts`: every cell slot (accessor, format, filterFn, sortBy) dispatches exactly one
  `column:batch` per column per read, with `where` = the slot path (R6 carry-over).
- `catalog.test.ts`: every registered code (enumerated through the public index) has a
  definition with `where` / `fix`, and is either produced by the harness (real diagnostic: non-empty
  `where` and `fix`) or listed with the test file that injects it (file checked to name the code).
  A new code with neither fails (R6 carry-over; T38 builds docs on top).

## Product fixes (test-first, each small)

1. R2: `DK_INTERNAL` classifier — own frames are `@datakable/`, `@datakable_` (Vite optimized
   deps), `node_modules/datakable/`, `.vite/deps/datakable…`; a user folder named `datakable*` is
   not DataKable code.
2. R4: a feature whose `createApi()` threw: in dev a calls to one of its (missing) methods is a
   no-op that reports `DK_FEATURE_FAILED` (`hook: 'createApi'`, `method`) instead of a raw
   TypeError (prototype proxy, installed only when a `createApi` failed; table identity unchanged).
3. R6: the §6.6 status rule as one named predicate (`diagnosticSetsErrorStatus`, pipeline module),
   plumbed through every in-step emit (step `ctx.emit` and the column cache), with sticky column
   cache entries and no memo for a flagged step. Default (orchestrator, pending the user's answer):
   in-step handled diagnostics do not flip status; a throwing step, failed ingest / fetch / search
   do. Flipping the predicate is the one edit.
4. Anything else the harness finds: a failing test first, the smallest fix, listed in the report.
