# T32 — React SSR: `initialState` / `initialData`, `getServerSnapshot`, `DK_HYDRATION_MISMATCH`, `DK_SSR_ASYNC_DEFERRED`, `DK_STATE_UNKNOWN_KEY`

Spec §7.2 (+ §6.6 status, §8.3 codes, §10 hook, §11 React SSR test).
Done when: `renderToString` with `?q=` is pre-filtered; hydrate without re-fetch.

## Design

1. **`initialData`** (core `TableOptions`, read once). The rows the server already produced for the
   initial state. Ingested at creation like `data` (schema, data checks; `isInitialLoad: false`)
   when `data` is not given (`DK_OPTION_NO_EFFECT` when it is). It counts as the result of the
   async work for the initial state:
   - the fetcher's first request is skipped (the creation params are recorded as fetched); a later
     server-state change fetches as usual; the server row count starts at `rowCount ?? length`
     (`rowCount` is no longer "no effect" with a fetcher when `initialData` is given);
   - a `searchFn` for the initial query is not called: `initialData` is its result.
2. **Deferred start** (core seam for bindings, `table/ssr.ts`): `createDeferred(() => createTable(o))`
   creates a table whose async work does not start: the fetcher's first request and the `searchFn`
   for an initial query wait for `startTable(table)`. While waiting the row model has
   `status: 'pending'` (§7.2). On the server (no `document`) each deferred source reports
   `DK_SSR_ASYNC_DEFERRED` (info). No request, no timer, no microtask chain is started.
3. **React hook**: always creates the table deferred (render is side-effect free; the React 18
   StrictMode extra table never starts a request) and starts it in its mount layout effect (before
   paint). On the server effects never run, so nothing starts and nothing leaks.
   `getServerSnapshot` returns the view captured at creation: derived from `initialState`,
   controlled `state` and `data` / `initialData`, never from async results — the same on the server
   and in the hydration render.
4. **`DK_HYDRATION_MISMATCH`** (warn): in an insertion effect of the hydration commit (before any
   layout effect can change the table), the view React hydrated with (server snapshot) is compared
   with the live one; differing state slices (or `rows` / `data`) are named. React re-renders
   after hydrating in that case, replacing the server HTML.
5. **`DK_STATE_UNKNOWN_KEY`** (warn): a `columnFilters` entry (initialState / state / API) on an id
   that is not a column is ignored (T13 TODO) and reported once, with did-you-mean.
6. `registerPackage('datakable', version)` on the first `createTable` / `useDataTable` of `datakable`.

## Tests first

- core `table/ssr.test.ts`: initialData ingest / no first fetch / later fetch / rowCount;
  deferred: no fetcher call and no timer until `startTable`, status `pending`, one
  `DK_SSR_ASYNC_DEFERRED` per source; searchFn deferred / seeded by initialData.
- core `column-filters.test.ts`: unknown id → ignored + `DK_STATE_UNKNOWN_KEY`.
- react `ssr.test.tsx` (node env): renderToString + fake timers → no timer, no fetch, no
  table started; StrictMode render.
- react `hydrate.test.tsx` (happy-dom): hydrateRoot with initialData → no fetch; without → one
  fetch after hydration; mismatch → `DK_HYDRATION_MISMATCH` naming the slice; clean → none.
- datakable `ssr.test.tsx`: `?q=` parsed into `initialState` → pre-filtered HTML (default preset).
- catalog completeness entries for the three codes.

## Out of scope

- Transmitting the server snapshot to the client (detecting `initialState` / `data` that differ
  between server and client): undetectable from the hook; React reports the text mismatch itself.
- `DK_STATE_UNKNOWN_KEY` for top-level `initialState` slices: custom store-owned slices are legal
  (§3.2, typed `S`; an existing test keeps them). Sorting ids outside `columns` are path sorts
  (T15), not unknown keys.
- `<DataTable />` markup / Loading for `pending` + `isInitialLoad` (T33).
- Worker search (`useWorker`), time-slicing `pending` (T29).
