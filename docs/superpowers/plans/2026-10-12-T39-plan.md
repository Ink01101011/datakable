# T39 plan — `apps/docs` playground on the real API

Done when: the playground uses `<DataTable />` and `useDataTable` (task table, T39).

## Steps

1. Test first: `apps/docs/src/App.test.tsx` renders `<App />` (happy-dom, @testing-library/react)
   and asserts the zero-config table, the four example sections and the diagnostics panel.
   Root `vitest.config.ts` gets a `docs` project (additive) that maps `datakable` to source.
2. `apps/docs/src/data.ts`: ~10k deterministic rows generated locally (no network), a fake async
   fetcher over them (latency, abortable, a fail switch) and a hand-written Standard Schema
   (no schema library dependency) plus raw rows with some invalid ones.
3. `apps/docs/src/App.tsx` sections:
   - Zero-config: `<DataTable data={rows} rowKey="id" />`.
   - `useDataTable` + custom render: status + isInitialLoad, `data-*` hooks.
   - Server mode: server search/sort/pagination with the fake fetcher; a toggle makes it fail;
     Error + Retry come from `<DataTable />` (`refetch()`), plus a manual Refetch button.
   - Schema flag mode: `schema` + `invalidRows: 'flag'`, validity filter, `data-invalid` rows.
   - Diagnostics panel: every `onDiagnostic` event from the examples.
4. Minimal inline CSS; one commented `import 'datakable/styles.css'` line for the reviewer
   (T35 is not on develop yet).

## Out of scope

- Any change under `packages/*` source.
- `datakable/styles.css` itself (T35), budgets / CI (T37), per-cell boundaries (T34).
- Routing, a docs site, deployment.
